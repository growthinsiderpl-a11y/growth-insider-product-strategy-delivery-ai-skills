# Journey Mapping Workshop

Plan and run a workshop that maps the current or target customer
journey in enough detail to expose pain, handoffs, and design
opportunities.

## When To Run It

- cross-functional teams disagree about where the journey breaks
- support, sales, design, and product hold partial views
- a workflow spans multiple steps or actors
- the team needs one shared view before rewriting requirements

## Do Not Run It When

- the team only needs a solo analysis memo
- there is no evidence to ground the workshop
- the workshop is being used to avoid making decisions
- participants do not include anyone with journey knowledge

## Inputs

- journey scope
- participants
- existing evidence
- timebox
- artifact format
- follow-up owner

## Procedure

### Define the Workshop Objective

- choose one journey and one decision focus
- state whether the map is current-state, future-state, or both
- bring enough evidence to prevent imagination from taking over
- limit participant list to useful roles
- define the output expected at the end of the session

### Prepare the Canvas

- set stages, actors, steps, emotions, blockers, tools, and data
  fields
- decide how evidence will be cited
- preload known facts versus open questions
- make room for backstage or internal handoffs if relevant
- prepare a short legend for unknowns and assumptions

### Facilitate Mapping

- start with the triggering moment
- walk the journey step by step
- capture user goals, questions, and risks
- mark breakdowns, delays, and trust moments
- separate observed reality from desired future flow

### Prioritize Findings

- cluster pain points by consequence and frequency
- link issues to product decisions or research needs
- identify quick fixes versus systemic problems
- retire tangents that do not affect the target journey
- capture unresolved debate for later evidence gathering

### Close with Action

- define the next artifact or decision
- assign owners
- set follow-up timing
- store the map where future work can reference it
- note which assumptions still need validation before design or
  delivery starts

## Decision Tests

- the workshop has a defined question
- evidence is present
- the map captures user context and consequences
- action items emerge at the end
- current-state facts are separated from future-state ideas

## Outputs

- workshop agenda
- journey canvas
- priority pain-point list
- follow-up action plan
- evidence-backed questions for discovery or design

## Failure Modes

- mapping every possible journey at once
- letting future-state ideation erase current-state evidence
- ending with no owner for follow-up
- treating the map as complete truth instead of a working model

## Review and Follow-through

- convert top pains into opportunity or requirement work
- run usability or discovery follow-up if needed
- refresh the map when the workflow materially changes
- archive assumptions that were disproven after the workshop

## Escalate or Stop When

- participants cannot agree on what trigger starts the journey
- future-state ideas crowd out current-state evidence
- the workshop expands to every persona and every workflow
- no one is assigned to convert insights into product decisions
  afterward

## Worked Scenario

- A workshop on first-team setup should map invite receipt, first
  login, policy review, and initial approval request, not only the
  in-app wizard.
- That broader path often explains why activation and retention
  diverge.
