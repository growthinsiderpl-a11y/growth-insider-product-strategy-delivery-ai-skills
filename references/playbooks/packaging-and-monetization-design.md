# Packaging and Monetization Design

Shape product packaging or monetization changes using explicit
trade-offs, customer evidence, and safe measurement rather than
guesswork.

## When To Run It

- plans, limits, or upgrade paths may need redesign
- customers are confused by packaging
- the team wants to improve conversion or expansion without
  harming trust
- board pressure is pushing monetization changes faster than the
  evidence

## Do Not Run It When

- the task is a promotional pricing campaign
- there is no user evidence about value or friction
- billing implementation detail is the main problem
- the team only wants competitor plan copying

## Inputs

- current plans or packages
- usage patterns
- conversion and expansion data
- customer evidence
- margin or revenue constraints
- risk notes

## Procedure

### Clarify the Monetization Job

- state whether the goal is conversion, expansion, retention,
  fairness, or operational simplicity
- name the user segment and buying context
- identify what value boundary the package should communicate
- note any non-negotiable business constraints
- state which product behavior should change if the design works

### Diagnose the Current Model

- check where users hesitate, downgrade, or overconsume support
- compare actual usage clusters with package boundaries
- look for confusion between feature access, capacity limits,
  and procurement logic
- document trust-sensitive moments
- separate product value issues from packaging clarity issues

### Design Option Set

- create at least two credible packaging structures
- show trade-offs across simplicity, upsell room, support
  burden, and fairness
- note what each option implies for product messaging and
  onboarding
- keep options reversible where possible
- surface any segment that may need a different treatment

### Prepare Measurement

- define primary and guardrail metrics
- segment by plan, tenure, or account type
- set review windows that match the decision
- plan support and customer-success feedback capture
- document how pricing and retention will be read together

### Recommend Rollout

- choose pilot, staged rollout, or broader release
- record open questions
- explain what would make the team reconsider the design
- align the outcome with roadmap and board narrative when needed
- state where marketing and engineering coordination begins

## Decision Tests

- options reflect real usage and value logic
- trade-offs stay explicit
- trust effects are considered
- measurement is planned before rollout
- coordination boundaries are clear

## Outputs

- packaging design memo
- option comparison
- measurement plan
- rollout recommendation
- customer-risk guardrail summary

## Failure Modes

- copying competitors blindly
- optimizing revenue while ignoring fairness or support burden
- assuming packaging can fix a weak value proposition
- treating one enterprise request as universal packaging truth

## Review and Follow-through

- coordinate with marketing on external communication
- coordinate with engineering on implementation feasibility
- review results by segment after rollout
- update board communication if the monetization move changes
  revenue posture materially

## Escalate or Stop When

- packaging is copied from competitors without evidence
- support burden rises in the segment expected to upgrade
- pricing language promises value the product has not proven yet
- plan boundaries punish the very usage that predicts retention

## Worked Scenario

- If governed approvals predict expansion, consider packaging
  around governance depth and audit control instead of adding
  arbitrary usage caps.
- That positions monetization around proven value rather than
  synthetic scarcity.
